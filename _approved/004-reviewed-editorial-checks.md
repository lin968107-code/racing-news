# 每天自动发布100篇文章需要怎样审核

## “最多100篇”不是“必须凑满100篇”

当自动发布系统设置每日上限100篇，正确含义是当天允许最多100篇已经审核合格的稿件进入公开目录。如果审核后只剩三篇，就发布三篇；如果一篇都没有通过，发布零篇同样正常。为了凑满配额反复改旧稿日期、替换标题或复制正文，不会增加真正有用的信息，还会让之后的内容维护难以区分原始版本。

## 质量检查从标题与正文对应开始

审核每篇文章时首先核对标题承诺回答什么问题，正文是否真正给出答案。比如标题提到站点地图抓取，就应该讲清楚XML地址、Pages部署、Google上次读取时间和错误状态；不能只写一段任何主题都能使用的“保存链接、核对日期”。其次检查具体事实是否可复查，有没有未经证实的官方认证、收益或服务安全宣称。固定的联系字段可以保留，但不应代替文章本身的主题内容。

## 防重复不能只比较文件哈希

完全一样的文件可以用哈希识别，但只替换关键词的两个版本，哈希往往不同。判断是否重复还应剔除共同的图片引用、页脚标识、相关文章导航，再观察主体段落、例子和结论是否只是同义替换。自动化可以提供初步相似度信号，却不能把相似度低就自动视为所有事实准确。对可疑稿件应让编辑进一步检查，并保留跳过原因。

## 发布程序如何应对重试

GitHub Actions定时执行可能延迟或失败，因此同一天的输出目录应有唯一日期标记。任务重新运行时要识别当天已有的文件，避免重复提交；同时应先成功保存公开文章，再移动审核队列里的原稿。如果发布程序中途失败，源稿不应被悄悄丢弃。多人同时修改主分支时，还要避免两个工作流使用同样输出位置造成提交冲突。

## 什么是可以验证的成功

自动工作流显示绿色成功，只能证明脚本运行结束；还要看实际提交了多少文章、是不是能公开打开、图片是否显示、相关文章目标是否存在。每天可以保留计划上限、审核队列数量、发布数量、跳过理由和文章链接清单。只有确认具体文件已在仓库中出现，才能称为完成了这批公开发布。Google或百度是否收录仍是另一项需要单独监测的工作。
