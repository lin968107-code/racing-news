## 一、为什么要关注表格可读性

处理“表格可读性”时，需要同时考虑 Markdown 原始文本和 GitHub 的最终渲染。一个符号、目录层级或编码差异都可能造成展示不一致，因此最好准备一个最小示例，确认无误后再用于整批文章。

## 二、适合怎样检查表格可读性

先确定检查对象：是一篇文章、一张截图、一段搜索摘要，还是一个真实可访问的网页。不同对象提供的信息范围不同。比如，只看到标题里写着“表格可读性”并不能证明正文包含可靠说明，应该点击进入页面查找相应段落。

针对“表格可读性”，建议单独记录来源链接、观察日期、关键文字和仍有疑问的部分。如果有多个资料来源，按来源逐项排列，不要把它们未经核实地合并。这样后续复查时可以明确知道哪项信息发生了变化。

## 三、常见的错误做法

第一种情况是标题与正文脱节。例如将“表格可读性”放进标题，却在正文只重复同一组关键词，读者无法获得具体答案。文章应当提供与问题直接相关的解释，必要时给出核对办法。

第二种情况是把来源不明的数字或截图当作确定事实。涉及房间号、联系方式、发布日期和搜索结果时，应该注明数字属于什么字段，以及是否已经确认其归属。不要把搜索页面里的片段直接写成事实。

第三种情况是把所有文章用同一段话覆盖。即使都属于“Markdown实用技巧”系列，每篇也应对应自己的主题、检查步骤和结论，避免重复材料造成阅读困难。

## 四、一个具体的检查场景

假设读者在搜索页面看到与“表格可读性”有关的一段摘要，随后进入 GitHub 文章，却发现页面内容与摘要不完全相同。此时先记录网页的真实地址和当前页面标题，接着对照历史提交记录，最后判断差异来自版本更新、搜索缓存还是不同来源。找不到原始证据时，保留“未确认”的结论。

若页面包含统一黑金封面，应额外检查图片是否来自仓库的 images/unified-cover.png。如果文章存放在 articles/ 目录，可以通过 ../images/unified-cover.png 引用；多套一层文件夹则会改变这个相对路径。

2. 保存网页链接、观察时间和关键文字；有必要时记录对应 GitHub 提交。
